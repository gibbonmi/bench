## What to build

Expose the selected interface through the planned doctor compatibility mode.
Deliver the local report, context fingerprint, live-check obligations, and safe input handling in one executable slice.
Keep the legacy doctor path unchanged.
The compatibility owner supplies the same typed facts and recovery classifications to later consumers.
The current command must remain useful while repair and automatic lifecycle integration are unbuilt.

Use the system-test owner's existing process construction with `BENCH_KIT`.
Do not infer live qualification from a successful command or from a declared configuration file.

## Acceptance

- [ ] The compatibility report names the explicitly selected CLI or desktop interface.
- [ ] An unknown active runtime remains unknown when a launcher version is available.
- [ ] The report names the active configuration home without assuming the other interface shares it.
- [ ] An unreadable effective setting reports unknown with its source.
- [ ] Diagnostics leave both user configuration homes byte-identical.
- [ ] An absent required repository asset reports its exact restoration action.
- [ ] An absent global Bench command reports the existing by-path route.
- [ ] A declared hook remains unverified until its live behavior is observed.
- [ ] An invalid interface operand exits 2 before configuration reads.
- [ ] Special files and dangling configuration links return a bounded diagnostic.
- [ ] An empty required configuration file receives a distinct result from an absent file.
- [ ] A path containing spaces and glob characters reaches the intended repository.
- [ ] A changed relevant context produces a different compatibility fingerprint.
- [ ] A personal model preference alone does not create a Bench configuration conflict.
- [ ] The inspection result never labels the whole active chat qualified.
- [ ] Control-bearing report fields cannot inject a terminal control sequence.
- [ ] Legacy doctor invocations retain their prior exit and output behavior.
