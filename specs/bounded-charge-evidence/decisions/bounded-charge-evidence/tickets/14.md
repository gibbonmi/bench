# Which physical container should store one evidence set?

Blocked by: #3
Type: Grill

### Question

Should one immutable Bench-specific packfile contain a versioned header, the canonical manifest, and exact uncompressed source bytes?
The reviewer permits a custom storage format and asks whether it improves the design.
The [container comparison](../assets/research.md#physical-container-comparison) compares a directory, ZIP, and a minimal packfile.
The recommendation keeps the logical identity independent of the physical container.
The format must remain documented and independently verifiable.

### Answer

One immutable Bench-specific packfile stores each evidence set in repository-common storage.
Its first version uses three ordered regions:

1. A fixed binary header contains a format marker, a container version, and the manifest length.
2. The manifest contains the exact canonical TOON bytes defined by ticket 12.
3. The payload contains exact uncompressed source bytes in manifest order.

The format is documented, versioned, and independently verifiable.
Logical page offsets remain relative to their source.
The reader derives physical offsets from validated lengths instead of maintaining a second offset registry.
It validates arithmetic, ranges, and the exact expected file length before returning a page.
It refuses unsupported versions, invalid or overlapping page ranges, truncation, and trailing data.

The artifact lifecycle and verification rules remain those defined by tickets 3, 10, and 12.
The container introduces no archive extraction, general database, or compression codec.
A later physical representation must preserve exact logical evidence bytes and their identity.
No custom-container benchmark or compatibility probe forms part of the accepted evidence.
The implementation must validate the production reader and writer.
