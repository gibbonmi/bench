# Does the artifact lifecycle preserve one immutable evidence identity?

Blocked by: #3
Type: Prototype

### Question

Can the selected artifact owner preserve one immutable identity through concurrent creation, cross-worktree reads, release, corruption, and cleanup?
The probe uses disposable storage and retains no production code.
It also records artifact sizes and the cost of verification for the resource-policy decision.
The [lifecycle proposal](../assets/research.md#lifecycle-and-hostile-storage) states the candidate outcomes.

### Answer

The reviewer accepts the lifecycle result as sufficient shaping evidence.
Implementation must validate supported platforms, production Bench assignment release, concurrent storage safety, and hostile filesystem behavior.
The Linux observations do not replace those production checks.

### Prototype observation

The disposable Linux probe passed 18 checks on 2026-09-15.
Four processes published identical content to one identity.
Distinct content published separately, and a sibling worktree read the same artifact.
Removal of the origin Git worktree preserved the evidence.
A changed tip invalidated the action pin while historical bytes remained readable.

The probe refused truncated bytes, replacement bytes, symlinks, FIFOs, and unexpected directories.
An interrupted temporary artifact produced no published identity.
A separate reader process held a shared lock, and cleanup could not acquire its exclusive lock.
After the reader released its lock, cleanup acquired that lock.

| Artifact bytes | Publication ms | Full verification ms |

| 1,048,576 | 5.69 | 0.86 |

The timings are single local observations, not latency guarantees.
The probe used disposable Git worktree removal, not production Bench assignment release.
It did not prove Windows or macOS behavior, adversarial filesystem races, or production integration.
The Answer section records the reviewer's acceptance and the required production checks.
