- 2026-08-01  REVIEWER RULING 2026-08-01: humans should not be interacting with the `bench` CLI in the vast majority of cases; there are exceptions, but worktrees is not one of them. `bench worktree` with no subcommand is currently a human porcelain — `Subshell` (`internal/worktree/worktree.go:412`) creates a worktree, prints `🪵 worktree: <path> (exit to release)`, runs `$SHELL` inside it with stdin inherited, blocks on `cmd.Run()`, and releases only after the shell exits. Under the ruling that bare form is the wrong default for this repo: the agent-facing surface is the subcommands (`list`, `path`, `exec`, `release`, `clean`, `recovery`), and worktree creation for agents already happens through `bench spec build assign` and the shift loop. Proposal: make the bare verb print usage like every other parser-first verb, and move the subshell behind an explicit opt-in name if it is kept at all. Two supporting facts. First, it silently traps automation — an agent probing for usage gets a two-minute hang and a SIGTERM, which is how this was found. Second, the release is NOT signal-safe: because it runs on the line after `cmd.Run()` returns, a SIGTERM or SIGINT to the `bench` process skips it entirely and leaks a registered worktree (observed twice; both retired afterwards with `bench worktree clean`, `count=0 bytes=0 recovery=none`). If the subshell is kept, the release needs a signal trap or a lease the resume path reclaims; if the bare form becomes usage, the leak surface mostly disappears with it.
- 2026-08-01  PRIORITIZE — `bench spec build` promote's precondition ORDER makes recomposition unreachable for the run that needs it, turning any mid-run commit to the working branch into an unrecoverable deadlock. `recompose := run.Base != subject.tip` (`internal/specbuild/precondition.go:46`) fires on ANY commit to the branch during an active run, and every operation (`assign`, `integrate`, `review`) then refuses with `errRecompose` pointing at `bench spec build promote`. But `Promote` (`internal/specbuild/assign.go:307-318`) checks, in order: (1) the review is clean — no accepted findings; (2) every assignment integrated AND released; and only then (3) the recompose branch. A run that is mid-repair satisfies neither of the first two by construction: its review has accepted findings (that is what a repair round IS), and its assignments cannot release because `integrate` itself refuses on `errRecompose`. So the mechanism built for "the branch moved" is gated behind conditions only an already-promotable run can meet. Observed: a ten-ticket build reached a full clean three-axis review, then deadlocked permanently after two necessary commits to main (the repair tickets, which must be committed before `assign` can resolve them, and a light-path lifecycle fix). Note the compounding trap: repair tickets MUST be committed to be assignable, and committing them is itself what triggers the deadlock — so the documented repair path cannot be walked. Fix: move the recompose branch ahead of the review and released checks, or expose recomposition as its own operation rather than burying it inside promote. Also worth revisiting whether a moved branch tip should block `review` at all, since a review grades the candidate, not the branch. ADDENDUM to the precondition-ordering defect above, and the reason it is severe rather than merely awkward: `abandon` is blocked by the same gate. `bench spec build abandon <slug> --apply <fingerprint>` returns `spec build requires recomposition` even though it plans cleanly and emits a valid fingerprint. So a deadlocked run cannot be started, assigned, checkpointed, integrated, reviewed, promoted, OR abandoned — all eight public operations route to `promote`, and `promote` is unreachable. The run record stays permanently `active` in the git common directory with its worktrees registered and its provisional refs retained, and there is no sanctioned way to retire it. Whatever the fix to the ordering, `abandon` in particular must never require recomposition: it is the lifecycle's own escape hatch, and an escape hatch behind the lock it is meant to escape is not one.
