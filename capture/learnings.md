# Learnings — usage journal

## 2026-08-06 - repair lifecycle repeats unchanged review and full gates  [open]
- **What happened:** One exact review found two concrete defects. Turning those findings into a repair required committing a process-only repair ticket through the whole-project gate, recomposing the unchanged defective implementation, and reviewing it again before assignment. A missing fenced-path anchor in the ticket was discovered only by `assign` after that gate; correcting the metadata required a second whole-project gate, another recomposition, and a third review of the same implementation. Separately, a delegate reported the full package green after changing a shared helper's key contract; a coordinator consumer-focused test found the regression before checkpoint.
- **Right behavior:** Pay for one defect-discovery review, one ownership-fenced repair assignment, one fresh whole-candidate review after the repair changes the composition, and one authoritative promotion gate. Validate lifecycle-only artifacts before an expensive gate, do not invalidate semantic review merely because unrelated control metadata changed, and make claimed command completion independently inspectable.
- **Proposed rule change:** Add a lifecycle-native repair operation that derives an ownership-fenced repair ticket or assignment from accepted review findings without first landing a process-only ticket on `main`. Preflight ticket grammar, `Contracts:` anchors, fence coverage, row closure, and assignability before any commit gate. Retain a review across recomposition only when the implementation patch/tree, approved spec digest, and reviewed inputs are byte-identical; otherwise invalidate it. Generate checkpoint/review receipts from lifecycle state (the existing FT184 direction) and retain structured command exit/output evidence so coordinators can verify completion without repeating broad suites. Keep the final fresh post-repair review and promotion gate; remove only unchanged-subject repetition.

## 2026-08-07 - lifecycle refusal advice sent a session to the wrong gate  [open]
- **What happened:** A concurrent capture-only commit (`ff3818b`) moved `main` mid-build; `promote` refused with `no exact green evidence: run bench gate --fresh, then retry promote`. The prior session followed that advice literally, forcing a full whole-tree gate for a capture-only diff; interrupting it overwrote `.git/bench-last-gate` with a pending record, permanently destroying the verdict record that would have proven which `ComposedGreen` subcondition originally failed. The resumed session ran plain `bench gate` instead: conformance-only partial, ~2.5 min, composed to whole-tree green, and the lifecycle completed through recomposition, repair checkpoint, re-review, and promotion.
- **Right behavior:** On a lifecycle no-exact-green refusal, run plain `bench gate` first — it self-selects scope and recovers pending, stale, and mismatched records; reach for `--fresh` only when a reusable green verdict exists but will not compose, and only with reviewer approval. Before signaling a running gate, preserve `.git/bench-last-gate` so diagnosis evidence survives the interrupt.
- **Proposed rule change:** Differentiate the refusal advice by cause (parked as idea, reviewer's call), and have gate startup preserve or embed the record it overwrites. Until then, treat CLI advice naming `--fresh` as a last resort, not a first step.
