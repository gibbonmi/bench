# Adversarial gate pinning (FT2)

Hash-verify the gate's enforcement surface outside the writable tree at push
time, closing the hole ADR 0001 scopes out: an agent that weakens the gate and
deletes the canary tripwire in the same diff. Posture stays the ADR's — loud,
not impossible; an agent with shell access can edit `.git/hooks` itself, and
that is out of scope.

## #1: What makes re-pinning human-only?

Type: Grill

### Question
A legitimate gate change needs a pin update, but if an agent can run the re-pin
command, weaken-then-repin defeats the feature.

### Answer
`bench gate pin` is TTY-interactive: it shows the `.bench` diff since the last
pin (or announces an initial pin), requires typed confirmation, and refuses
when stdin is not a TTY. Faking a TTY is a deliberate hostile act, not a
shortcut a grinding loop drifts into. Rejected: env-var override on push
failure (agents copy overrides from error messages); OS-privileged pin file
(privilege separation Bench doesn't otherwise require).

## #2: What does the pin cover?

Type: Grill

### Answer
The git tree hash of `.bench/` at the pushed commit
(`git rev-parse <oid>:.bench`). That is the declared oracle-and-enforcement
surface — gate entry, hooks, lib, lines.env — in one native primitive. Deeper
logic (the kit's Go core, a consumer's test suite) stays defended by the
tripwire plus review; repins happen exactly when enforcement files change,
which is the reviewable event. Rejected: `gate.sh` blob only (hooks and lib
ride through unpinned); configurable path manifest (the manifest becomes an
agent-editable surface).

## #3: Which pushes are verified?

Type: Grill

### Answer
Every pushed ref: hash `.bench/` at each pushed commit; any mismatch blocks
the whole push with repin instructions. Default-branch-only never sees an
agent's work (agents can't push it at all); the friction is the feature — a
gate change can't leave the machine until a human has looked. Rejected:
warn-on-branch (a warning in push output is what a grinding loop ignores).

## #4: Where does the pin live, and what happens unpinned?

Type: Grill

### Answer
`<git-dir>/bench-gate-pin`, a small file beside the existing `bench-last-gate`
cache — untracked, survives relink, room for hash + pinned-at commit +
timestamp. Unpinned repos pass with a one-line stderr notice
("gate unpinned — bench gate pin to enable"): pinning is opt-in; a hard block
would break every consumer on upgrade. Rejected: git config key (flat, awkward
for metadata); embedding the hash in the hook file (relink clobbers it);
block-until-pinned; silent pass.

## #5: Where does verification logic run?

Type: Grill

### Answer
Inline bash in the managed pre-push hook — pure git, ~5 lines, no exec into
tree-resident code. This deliberately breaks the hooks-call-plumbing
convention: the verifier must sit in the same trust domain as the pin, or the
agent weakens the verifier instead of the gate. `bench gate pin` (the writer)
stays normal Go plumbing since repin is human-attended. Rejected: hook calls
`bench` plumbing (verifier becomes agent-writable); duplicate inline check +
verify verb (two derivations of one fact).

## #6: Who gets the new hook?

Type: Grill

### Answer
FT2 updates the managed hook template in `bench link` (consumers get it on
relink) and reinstalls the current managed hook in this repo in the same
build — the kit dogfoods the pin immediately and the stale "no manifest"
guards row disappears. FT10 (doctor *detects* a missing/stale kit hook) stays
a separate capability. ADR 0001's "pinning is out of scope" paragraph is
updated in the same build to record the shipped state.

## Handoff

1. **Module boundaries.** (a) The managed pre-push hook template (generated by
   `bench link`'s hook installer): owns verification and the unpinned notice,
   inline. (b) A new human-run `bench gate pin` verb: owns pin creation and
   re-pin, including diff display and TTY confirmation. (c) The pin file
   `<git-dir>/bench-gate-pin`: hash + pinned-at commit + timestamp. Outside:
   doctor detection (FT10), gate content itself, any CI-side enforcement.
2. **Contracts.** Hook: per stdin ref line, skip deletes (zero local oid);
   compute the pushed commit's `.bench` tree hash; no pin file → one stderr
   notice, allow; hash mismatch or `.bench` absent at the commit → stderr
   message naming `bench gate pin`, exit 1; default-branch block retained;
   `--describe` manifest advertises both denials. Pin verb: refuses
   non-interactive stdin with a structured error; on a TTY, shows the `.bench`
   diff from pinned commit to HEAD, requires typed confirmation, writes the
   pin from HEAD's committed tree (never the working tree); dirty `.bench`
   gets a warning; declining writes nothing and exits non-zero.
3. **Deep vs thin.** The hook's verify block is deliberately self-contained
   (trust-domain rule — #5); it is the one Bench hook that must not exec
   plumbing. `bench gate pin` is a deep verb hiding diff/confirm/write;
   `.bench/gate.sh` is untouched.
4. **Black-box assertables.** In throwaway fixture repos: pinned + unchanged
   `.bench` → push allowed; pushed commit with modified `.bench` → push blocked,
   exit 1, message names the repin verb; unpinned → allowed with the notice
   line on stderr; ref-delete push → skipped, allowed; pin verb with non-TTY
   stdin → structured error, no pin file written; after a TTY pin, the pin
   file holds the current `.bench` tree hash; `--describe` output lists the
   pin denial; `bench guards` on this repo shows a manifest row again.
5. **Gate attachment.** The runtime/behavior contract fragments that already
   exercise `bench link`'s hook install and pre-push behavior in throwaway
   repos; the conformance layer checks the template text where it checks the
   installer today. The TTY *confirm* path is the one seam the gate can't
   drive directly — test the refusal (non-TTY) path in the gate and flag the
   confirm path for a PTY helper or manual verify.
6. **Hostile-input owners.** Hook: paths/branches with spaces (quoting), zero
   oids on deletes, commit with no `.bench` tree, multiple refs in one push,
   absent vs present-but-empty vs malformed pin file, no `bench` on PATH
   (inline bash needs none). Pin verb: re-run idempotency (pin twice), dirty
   `.bench` working tree, detached HEAD, repo with no commits.
7. **Uncertainty flags.** TTY confirm-path testability (PTY helper vs manual
   verify) — spec must pick and say so. Exact pin-file format is open but
   small; the spec decides it, it is not a fork.
8. **Rejected alternatives.** Env-override repin; OS-privileged pin file;
   `gate.sh`-blob-only pin; configurable path manifest; default-branch-only or
   warn-on-branch scope; hook execing `bench` plumbing for the check;
   embedding the hash in the hook; block-until-pinned; silent unpinned pass;
   folding FT10's doctor work in.
9. **Domain watch-outs.** Pre-push verifies the *pushed commits'* trees, never
   the working tree — `git rev-parse <oid>:.bench` semantics. The pin is
   per-clone: a fresh clone is unpinned until its human pins (accepted —
   opt-in posture). The threat model stops at "loud": `.git/hooks` is
   agent-writable in principle and defending it is out of scope (ADR 0001's
   posture, restated).

Dependency order: n/a — single spec.
