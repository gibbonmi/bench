# How does the work split across existing owners?

Blocked by: #3, #4, #5, #6, #8, #9
Type: Grill

### Question

Choose one coordinating spec with amendments or separate owner specs. The
possible owners are FT173 projections, FT231 measurement, FT89 operating
guidance, FT100 guidance weight, and new worktree operations. Preserve one
source for each budget, metric, parser, and command policy.

### Answer

The reviewer approves one coordinating spec with four child specs.
The coordinating spec owns the outcome map, dependencies, and reviewer checkpoints.
It links each child's requirements rather than copying them.

| Child spec | Deliverable outcome | Existing owner |
| --- | --- | --- |
| Measurement and budget evidence | Capture reliable measures and replay representative cases for budget review | FT231 and its harness reader |
| Bounded reads and multi-target queries | Return task-shaped reads, worktree facts, and bounded spec histories | FT173 with focused FT89 guidance |
| Verified harness overflow | Preserve complete output and replace oversized results only at verified boundaries | The harness integration, with FT231 measurement |
| Set-wide worktree cleanup | Plan and apply one selected set with one fingerprint and per-target outcomes | The existing worktree lifecycle owner |

The measurement child supplies evidence for the review checkpoint in ticket 9.
Budget-dependent default behavior waits for that review.
The overflow child preserves the capability and fallback requirements in tickets 3 and 6.
Cleanup can proceed independently of new result-budget decisions.

Focused guidance covers the approved read practices and archive/log batches.
FT100's general guidance rewrite remains excluded.
Each budget, metric, parser, and command policy retains one source.
The split does not authorize implementation or bypass any child spec's approval.

The reviewer confirms this structure as the shared understanding for spec authoring.
