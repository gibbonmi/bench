**FT214 (MEDIUM) — `craft-spec` visit: fences the build may not move, one source per fact, and rows that prove what they claim.**
One kit edit under `craft-synthesis` over a single owner surface, batched
because each clause separately pays a full gate for a few lines.

A build may not edit its own spec's acceptance rows, budget targets, or
ownership fences. A build hitting a spec-level shortfall stops and returns to
`/bench-write-spec` — the material-acceptance-shortfall predicate applies even
when the change sits inside the spec's own fences. A gate-visible check is
possible: a budget row whose value equals the current line count of its subject
proves nothing, because the check parses only that one source.

Specs name enumeration sources instead of copying implementation-derived counts,
and Standards grades restated counts.

When a spec's own justification is that behavior is preserved, its exit row names
a differential run of the old and new implementations over one enumerated input
family rather than resting on "the pre-existing suite passes" — a suite cannot
protect behavior it never asserted. When a spec introduces an ordering or
grouping requirement over a collection that had none, the row set fixes the
cardinality at that concept edge (can one member carry two?) with a fixture
exercising the many case, because the natural implementation of "ordered by key"
quietly answers one. That last clause is `craft-domain`'s.

A coverage row promising that output "names the command" pins the exact command
token, never the family, so the cheapest wrong build cannot still pass it. A spec
adding a standing check enumerates the in-flight tree states that check must
tolerate, drawn from the same spec's own lifecycle, so the check does not red on
a state the spec's own close step creates. When a ticket replaces a blunt check
with a precise one, the coverage map adds a row for the parse surface the
precision creates — rows inherited from the blunt check cannot mention a surface
that did not exist when they were written. A claim that something is or is not a
tree convention cites the check that enforces it, not a sample of artifacts that
happen to follow it; an absence in the sample is not evidence of an absent rule.
When a row names a failure mechanism, it traces the message to its producer and
confirms the claimed input can reach that producer; occurrence evidence about an
operator session cannot establish tree reachability.

Two map-discipline clauses close the read-before-cite gap on the test side. A
row whose seam is "existing tests" names the test function, verified by a read
this session — the rule already applied to code was not applied to the tests a
coverage row names. And a spec that deletes literal bytes runs one repo-wide
search for those bytes, canary fixtures included, before the map is written.

Three further clauses. Naming the test function is not enough when the row also
names a technique: a row whose seam substitutes a package-var also names the
venue, because a substitution in the test process reaches nothing inside a test
that drives a real subprocess, and the row reads as complete until someone opens
the test. An ordering or before-and-after promise needs a row where two refusals
compete and the map names which message wins; a row asserting only that nothing
mutated cannot distinguish the first read-only position from the last. And the
ownership fences are derived from the tickets' own `Writes:` lines rather than
authored separately, so a file the design needs cannot be missing from the fence
that authorizes it.
