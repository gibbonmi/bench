**FT234 (HIGH) — a pool key whose source repository is gone can be reclaimed.**
`Pool(root)` is a one-way checksum and `benchHome()` has exactly one caller, so
every production read of the worktree pool is addressed from a live repository
root. Nothing enumerates `$BENCH_HOME/worktrees` itself. A key whose source
repository was deleted is therefore unaddressable rather than merely unnoticed,
and no reconciler predicate can reach it — the intent ledger that would name it
lived inside the deleted repository. Bench gains a home-scoped reader and one
plan-before-apply verb that reclaims such keys, and reports their count at
resume without ever removing them automatically.

Occurrence: 2026-08-19, during the FT226 landing — five dogfood pool keys
(23 MB) pointing into deleted `/tmp/bench-dogfood-*` repositories, plus three
empty keys, survived every `bench resume` in the operator's pool.
Occurrence: 2026-08-19 repro — a dangling-pointer child planted inside the key
of a live, current repository also survives `bench resume-clean`, so the gap is
that pool bytes are never walked, not that dead roots are unreachable.
