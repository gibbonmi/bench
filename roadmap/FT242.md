**FT242 (HIGH) — inherited environment markers cannot hide a required toolchain.**
A harness process can inherit Envman's loaded marker without the PATH effects
that marker promises. In the reproduced Codex client, native Go existed at its
configured Linux location and a clean login shell found it, while the client
environment omitted that directory and retained `ENVMAN_LOAD=loaded`. A
Git-source Bench build then cannot find Go, and Go-backed project gate phases
must not disappear into a weaker apparently-green result.

Add one environment-closure rule across the existing owners. SessionStart
diagnoses a repository that requires Go when the harness PATH cannot resolve it
but a clean login shell can, and prints a copy-paste recovery that prepends the
recovered directory without replacing the ambient toolchain. Gate staging fails
visibly whenever a required toolchain is absent, independent of harness. A
system regression reproduces the inherited-marker/reconstructed-PATH shape, and
agent guidance preserves the complete ambient PATH during recovery. Test the
Codex client and CLI against the same WSL repository and toolchain before making
the portability claim.

Occurrence: 2026-08-21 Codex client repro — the process inherited Envman's loaded marker without its Go PATH entry; clearing only the marker restored Go in the same login shell, while replacing PATH during recovery caused a second tool-discovery failure.
