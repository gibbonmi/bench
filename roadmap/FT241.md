**FT241 (LOW, decision required) — versioned acceptance promises with retained evidence.**

Represent the important end-to-end promises as reviewable, versioned files in
the repository — narrowly, and later. Candidate promises for Bench and the EKS
platform: a new application completes onboarding from the supported
configuration format; a resumed implementation retains its declared line,
ownership fence, and verification state; and a model or harness swap loses no
authoritative work state. Also candidates: a promotion cannot succeed with
missing or stale required evidence, and skipped validation stays visible in
the final result. Each
run records the promise version, target revision, and environment. It also
records observations, verdict, skipped coverage, and evidence locations.

The boundary is hard and pre-decided. Use deterministic tests whenever the
promise can be codified; reserve agent-driven acceptance for genuinely
behavioral workflows whose implementation details should be allowed to change.
Agent acceptance belongs beside `/bench-final-check` — it never becomes the
deterministic gate. IntenTIC's gate semantics (an agent's pass/fail/blocked
verdict, with blocked creditable as a CI success) do not enter under the Bench
gate name. If Bench ever adds an AI-mediated CI decision, it is called review
or advisory-check. The authority line stays: final-check evaluates meaning,
completeness, and risk; the gate deterministically verifies required proof and
invariants.

extension and gate-terminology boundary; assessment prompt only — the IntenTIC
tree was not read).
