**FT254 (MEDIUM, decision required) — `bench worktree exec` is the comfortable path for multi-step work.**

Preserve the exec-comfort decisions after the census spec retires. The exec
help shows stdin with a heredoc example. `bench worktree show
<target> <rev>:<path>` prints the blob bytes unchanged. Every exec failure after
target resolution prints the absolute worktree path; an earlier refusal names
`bench worktree list`.

Add `bench worktree resolve <target> <path>...` for caller-edited conflicts. It
stages paths without conflict markers and reports the remaining unmerged paths.
The reviewer must decide whether it also continues a merge, cherry-pick, or
revert that Bench did not start. The follow-on guard names the token that caused
a refusal and does not classify a heredoc body with no `bench` word as a
follow-on.

`bench worktree exec --env KEY=VALUE` supplies worktree-local inputs without
caller variables. An assignment retained after release stays resolvable by
`exec`, or release names the reachable recovery verb.

An exec-native gate form avoids raw `bash bin/bench.sh gate`. A declared
environment and tool-closure form supports focused package reproductions.

`bench worktree create --from <target>` starts a new assignment at a sibling's
tip in one step, and the bare `bench preflight` `base-current` red names
`bench worktree merge` as its `next=` remedy. Both are the out-of-scope cuts
the worktree-merge spec declined, folded here when FT252 retired.

`bench worktree exec` as a pass-through child accepts a non-bench follow-on
step, so a cp-aside probe costs one call. The follow-on guard names the
segment it refused. A worktree's own grammar runs through `bench worktree exec
<label> -- ./dist/bench`, or a `bench worktree build <label>` form; the
wrapper on `PATH` serves the main checkout's build.
