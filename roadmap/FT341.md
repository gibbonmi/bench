**FT341 (HIGH) — each Bench verb declares its tree scope, and a tree-scoped verb takes an explicit target.**

The command registry classifies each Bench verb as tree-scoped or repository-scoped. A
tree-scoped verb, such as `commit`, `preflight`, `coverage`, or `gate`, takes `--in <target>`.
It refuses the primary checkout when it needs a worktree. Each tree-scoped response names the
tree that it graded. A repository-scoped verb, such as `help`, `status`, `idea`, `learning`,
`handoff`, `worktree list`, or `worktree create`, takes no target.

The target contract replaces ambient root inference. A tree-scoped command
reads configuration, source, and registries from the named tree. Each response
identifies that tree. A caller does not bind a pool path in a shell variable or
depend on the installed binary's source tree.

`bench anchors` reads the registry from its named worktree. `bench gate-prose`
and the review preflight also resolve their subject from the named tree. This
keeps a worktree change from being graded against the primary checkout or a
stale installed registry.

`internal/canonicalpath` owns Bench's canonical-path derivation.
`internal/gate` still has a `resolvedPath` helper without an `Abs` step. The
target-contract decision must preserve the current behavior or explicitly
adopt the canonical derivation.

`bench worktree exec` then carries only commands that are not Bench commands. This removes most
nested exec calls and the wrong-tip class that FT254 records. A `bench worktree list` filter,
for example by spec, is a separate face for related-worktree navigation.

The change touches every hook and every skill that calls Bench, so it needs shaping. FT336
ticket 1 lands first: its spec is staged, and exec still carries non-Bench children, so the
exec output bound stays necessary.
