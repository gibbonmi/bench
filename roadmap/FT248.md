**FT248 (MEDIUM) — a Bash guard denies a shell follow-on appended to a `bench` command, and the rule states why.**

Agents still append a pipe, a redirection, an `&&`, a semicolon, or an extra
subcommand to a `bench` invocation, although `.bench/BENCH.md` forbids it. The
rule is prose only, so it does not bind; every other hard rule has an
enforcement hook. The reviewer set the scope: a `bench` command takes no added
option, no pipe, no redirection, and no `&&`. A `bench` response is designed to
be read on its own.

The cause is a reflex, not a measurement: the agent appends the follow-on
before it knows the output length, as insurance against an unbounded read.

Two levers, in priority order. First, a PreToolUse Bash guard beside
`block-dangerous-git.sh`: a thin shim over a `bench` core verb with the same
fail-open rim. It denies a Bash command that invokes `bench` and also carries a
pipe, a redirection, an `&&`, a semicolon, or an appended subcommand. The deny
message states that the `bench` response is complete and self-contained, so
the agent does not retry a variant. The guard parses the whole command line,
because a follow-on after `bench worktree exec <label> -- ...` can sit outside
the `--` and still apply to `bench`. Second, the rule's text in every place it
appears states the reason: a `bench` response is already bounded and complete.
Do not answer this with a projection option such as `--brief`; that concedes
the premise the rule denies.
