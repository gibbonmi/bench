User documentation · agentic development, made accountable

How Bench keeps an AI coding agent honest

Coding agents are fast, confident, and unsupervised, which is exactly the problem. An agent will happily declare its own work finished, quietly burn an expensive model on trivial edits, and write documentation only it can understand. Bench is a workflow kit that closes those gaps. An external gate decides what "done" means, declared budgets bound every long run, and a small set of commands and skills give the agent a repeatable way to shape, build, review, and ship work you can trust. Read this page top to bottom; each station starts with the core idea and unfolds into detail.

Start here

The mental model: two roles, four kinds of pieces

Everything in Bench follows from one division of labor. The agent is the worker; you are the reviewer, and you own the merge. The worker builds on your behalf but never decides what ships, what a spec should say, or anything irreversible. When a decision is genuinely yours, it surfaces the question and stops. Around that agreement sit four kinds of pieces, each answering a different failure mode of agentic work:

Guidance

Skills

Shape how the agent generates: the craft disciplines it reaches for when a task matches. Probabilistic guidance, not rules.

Process

Commands

The canonical phases of the workflow, from shaping an idea through the final check, plus maintenance passes you invoke deliberately.

Enforcement

The gate & hooks

Checks with authority the agent does not have. The gate decides "done"; git hooks protect the main branch no matter who pushes.

Operations

The bench CLI

The operational layer the agent drives: worktrees, the gated loop, status, and capture, with the same behavior in every harness.

Why this shape

Guidance can be ignored, so it never carries safety. Enforcement can't be ignored, so it carries all of it. Commands make good process cheap to follow, and the CLI makes the mechanics identical whether the agent runs in Claude Code, Codex, or any other harness. When you know which kind of piece you're looking at, you know how much to trust it.

2
Foundations

The four invariants

Four rules override convenience in every session, every phase, every harness. Each one exists because agents fail in a predictable way without it.

The gate is the oraclethe agent never grades its own work
The problem

A model judging its own output is circular: it built the code from the same understanding it now uses to approve it, so its blind spots pass their own review. "Looks correct to me" is precisely the signal that fails when it matters most.

How it works

"Done" means bench gate exits zero: tests, types, lint, and any project conformance check, all external to the model. If the gate is red, the work is not done, no matter how good the diff looks. The agent may never edit, skip, weaken, or delete a check to get to green; if a check seems wrong, it stops and says so. The rule extends to delegation: a subagent's "done" is a claim, verified against the gate and git status before it's accepted.

Declare the lineno silent escalation of model or effort
The problem

Long agent runs have real costs, and left alone an agent will spend a top-tier model on routine plumbing, or grind indefinitely on a problem it can't crack. You find out from the bill, or from a stuck session, after the fact.

How it works

Before any multi-cycle stage, the agent states one line: which model tier (cheap / mid / top), what effort, and a rough iteration cap, with a clause of justification. Cheap model for plumbing at a known seam; top model only where the answer is genuinely uncertain. If the cap runs out, the agent stops and reports rather than grinding. The abstract tiers are bound to real model ids per repo, so the budget survives model churn.

Document for the teammate who just walked inevery agent session starts with amnesia
The problem

Agent sessions have no memory of each other. Documentation written as change-narration ("we moved X to Y") is useless to a reader who never saw the before-state, and every future session is that reader.

How it works

Project docs and decision records describe the current decided state, addressed to someone with no memory of how it got that way. History lives in git, where it's already recorded. Decision records carry no file paths or code snippets, because those rot the moment the code moves.

One small change at a time, repo stays greensmall diffs are the reviewable unit
The problem

Agents can produce enormous diffs in minutes, and an enormous diff is unreviewable: the reviewer either rubber-stamps it or blocks everything. Worse, an agent that wants a shortcut will quietly reframe the task until the shortcut looks legitimate.

How it works

The smallest diff that advances the objective; commit on green, never on red. The agent reads the surrounding code before writing, and prefers composing an existing seam to inventing a new one. It is also taught to watch for one tell: if it catches itself reframing the task to make a shortcut feel acceptable, that reframing is the signal to stop and ask you.

3
Vocabulary

How Bench builds: at the seams

Bench takes one development approach everywhere, and it fits in a sentence: the spec chooses a small number of seams before the build starts, the build does test-driven development only at those seams, modules stay deep so the seams stay small, and the gate judges the result. The point of the arrangement is that the test target is external to the agent. You chose the seam and the behavior, so a passing test means the code matches your spec rather than the agent's own guess. The terms below carry that approach, and you will meet them everywhere: in specs, in reviews, and in the agent's explanations.

a well-placed seam
new Scheduler(clock).nextRun()

Time enters through the constructor, so a test injects a fixed clock through the same seam callers use.

a missing seam
nextRun() { return Date.now() + this.interval }

The dependency is hardwired. A test has to patch Date.now behind the interface, binding itself to an internal.

Seamwhere behavior can change without editing in that place

The place where you can change behavior without editing in that place. It is where a module's interface lives, and where callers and tests both cross. Placing the seam is a design decision in its own right, separate from what goes behind it: a well-placed seam makes tests cheap and stable, and a badly placed one makes the suite break on every refactor. Bench deliberately avoids the word "boundary", which means too many things.

Interfaceeverything a caller must know to use a module

The full contract a caller depends on: signature, invariants, ordering, error modes, configuration, performance. The smaller the interface, the less every caller, and every future agent session, has to learn.

Deep modulea lot of behavior behind a small interface

A module that hides a lot of behavior behind a small interface. Depth is the design goal, for two payoffs: leverage, where callers learn a little and get a lot, and locality, where changes concentrate in one place instead of rippling across the codebase.

The deletion testdoes this module earn its existence

The quick check for whether a module earns its existence. Imagine deleting it: if the complexity simply vanishes, it was a pass-through and shouldn't exist; if the complexity reappears across its callers, it earned its place. A related rule keeps speculative seams out: one adapter is a hypothetical seam, two adapters is a real one.

The interface is the test surfacetests cross the same seam callers use

Tests cross the same seam callers use and assert observable behavior, never private internals. If a test wants to reach past the interface, the module is the wrong shape, and the fix is to reshape it rather than reach around it.

TDD at the seamstest-first only where the spec marked it

Test-first development happens only at the seams the spec marked, never everywhere. At a marked seam the target is external, so passing the test means matching the spec. Off the marked seams, the agent writes the code and lets the gate catch regressions, which keeps the ceremony where it pays for itself.

Red, green, refactorthe cycle at a marked seam

Red: one failing test through the interface, confirmed to fail for the right reason, meaning an assertion failure rather than a compile error. Green: the smallest change that passes it. Refactor: clean up with the test still green. A good test survives the refactor; one that breaks was attached to an internal and gets re-placed.

Red signalproof that coverage is real

The evidence that coverage is real: a check that demonstrably fails when the behavior it maps is absent or wrong. A test that cannot go red proves nothing, so every acceptance row has to name one.

Acceptance coverage mapeach story mapped to its red signal

The table in every spec that maps each story to its red signal. During the build it is the unit of TDD coverage and the thing that keeps the target fixed: rows go red one at a time as each slice starts, never batched into an upfront pile of failing tests.

Edge inventorythe enumerated ways inputs can go wrong

The enumerated ways a seam's inputs can go wrong: hostile inputs, error paths, and the domain's own edge classes. The spec's stories are the breadth floor, not the ceiling. When the build finds an edge the spec forgot, it proposes a new coverage row for your veto instead of silently skipping it.

Over-fittinggreen but wrong

The characteristic failure of TDD with agents: the loop invents its own test target, writes the minimum to pass it, and stops, green but wrong. The guard is that seams and semantics come from the spec, never from the loop. An agent that catches itself inventing a target mid-loop treats that as the signal to stop.

Honest test doublesmocks only at real system boundaries

Mocks and fakes belong only at real system boundaries such as time, randomness, network, and filesystem, never on internal collaborators, and never asserting call counts or call order. A stub scripted to return exactly the happy reply hollows a test out, so stubs keep realistic shapes and fail in the ways the edge inventory says the real dependency fails.

Vertical sliceone story at a time, each ending green

The build order inside implementation: one story at a time, cut through the whole stack, each slice ending on a green gate. Every slice is reviewable on its own, which is what keeps the repo green between commits.

Design it twiceseveral interfaces drafted for the uncertain seam

The rule for a genuinely uncertain seam: don't settle for the first interface idea. Several radically different designs are drafted in parallel and compared before one is chosen. This is exactly what a declared high-effort line buys; at a known seam, one design is fine.

The structure gatesize budgets for files and directories

bench structure flags files and directories that outgrow their budgets. Splits follow responsibility, never line count, and a genuinely deep module can earn a reviewer-approved budget grant instead of being fragmented to dodge the limit.

A feature, end to end

The spec names the seams and writes the coverage map, and you sign off. The build declares its line, then works vertical slices: each row's red signal goes red, the smallest change turns it green, and a refactor pass cleans up behind it. Review checks what the gate can't see, and the final check runs the gate and commits. At every step the thing being satisfied is a target you chose, which is what makes the output trustworthy.

4
Architecture

The machinery that enforces it

The invariants would be wishes without teeth. These components are the teeth, and deliberately, the ones that matter work independently of any particular AI harness, so the safety doesn't evaporate when you switch tools.

The gate loop: who does what, and when
You
Once, at setup

Define what "done" means

During /bench-setup-repo you decide what the gate checks (tests, types, lint, conformance) and that becomes .bench/gate.sh. From here on, nobody improvises verification: every session defers to this one script.

Agent
Every iteration

Make one small change

The smallest diff that advances the spec, in its own worktree, so that the verdict coming next answers for exactly one diff and nobody else's edits.

Agent
Every iteration

Ask the oracle, don't judge

The agent runs bench gate after the change (the shift loop runs it automatically after every iteration). Its job is to report the verdict, not to form one. "The code looks right to me" carries no weight here.

Gate
Every iteration

Answer with an exit code

The gate runs the checks and exits zero or nonzero. That exit code is the entire vocabulary of done-ness, and no amount of model confidence overrides it.

exit nonzero · red · back to step 2

The work is not done, however good the diff looks. The agent keeps iterating; in a shift, an iteration that ends red is rolled back entirely. What it may never do is edit, weaken, or delete a check to reach green. If it believes a check itself is wrong, it stops and tells you.

exit zero · green · continue

The only state in which a commit may happen. bench commit stages the named paths; the shift loop commits on its own. Green means the external checks passed, nothing more, so the work still goes to review.

You
End of the phase

Review, then merge

A green gate earns a commit, not a merge. /bench-review-implementation checks what the gate can't see (spec fit, design, duplication), and the merge stays physically yours: the pre-push hook blocks anyone, human or agent, from pushing straight to main.

So how does the agent know to approve the work?

It never does, and that is the design. Two verdicts matter and the agent owns neither: the gate's exit code decides done (whether work may commit), and you decide shipped (whether it merges). The agent's belief that the code works is never a completion signal. It applies the same rule to its own subagents: a delegate saying "done" is a claim, and the claim is re-checked against the gate and git status before it's accepted.

The components
The gate (.bench/gate.sh)one script that defines "done" for this repo
The problem

Every repo has a different definition of correct: its own tests, type checker, linter, conformance rules. Without one agreed entry point, each agent session improvises its own verification, and improvised verification gets skipped.

How it works

bench gate runs the project's gate script and exits zero or nonzero, and that exit code is the entire vocabulary of done-ness. You configure what's inside it once, during setup; after that, agent, hooks, and loop all defer to the same oracle. Changing what the gate checks is itself a disciplined act, covered by its own skill, because whoever edits the oracle edits the meaning of "done".

The bench CLIthe operational layer the agent drives
The problem

If workflow mechanics live inside one AI tool's configuration, they behave differently, or not at all, in the next tool, and the human ends up doing clerical work (parking ideas, checking status) that the agent should absorb.

How it works

One CLI, driven by the agent, with harness-independent behavior. Its subcommands group into: adoption (link, init, doctor), ambient context (status, dashboard, roadmap, learnings, idea), oracle and diagnostics (gate, canary, structure, guards, coverage, models), and work execution (worktree, shift, path-scoped commit, and the spec lifecycle). You never need to type these yourself; the agent runs them and reports.

The shift loop (bench shift)an unattended build loop that can only commit green work
The problem

Letting an agent iterate unattended is where the leverage is, and also where the risk is. An unsupervised loop that commits its own unverified output will cheerfully stack broken commits all night.

How it works

bench shift drives whatever harness you point it at; a small adapter maps the generated prompt to that tool's noninteractive mode, and reference adapters ship for Claude Code, Codex, and OpenCode. After every iteration it runs the gate, and it commits only on green. In a repo with a tier binding, the adapters refuse to run at all unless an explicit, bound model is declared, so a headless run always carries a budget rather than a default.

Worktrees (bench worktree)one isolated copy of the repo per stream of work
The problem

When two writers edit the same checkout, whether that's you and an agent or two agents at once, their changes interleave. A gate verdict over a mixed tree answers for nobody's diff, and a delegate's stray edit can land silently in files you own.

How it works

bench worktree gives each stream of work its own git worktree, a separate directory sharing the same repository. Side-work and write-delegations go to their own worktree, so every gate verdict answers for exactly one diff and stray edits physically cannot reach the main checkout. Worktrees are pooled and reconciled on resume, so they're cheap to hand out.

Layered git safety (hooks)protection that survives a harness swap
The problem

AI-tool safety settings only bind that one tool. An agent run from a different harness, or a human in a hurry, can push straight to main, run destructive git commands, or stop a loop mid-red, and nothing objects.

How it works

Safety is layered from most to least universal. A git pre-push hook blocks direct pushes to the default branch for any pusher, and can pin the enforcement files themselves against drift. Where the harness supports hooks, extra interactive guards wire in: one blocks destructive git commands (force-push, hard reset, history rewrites), one blocks delegating to a model outside the bound tiers, one blocks stopping an armed shift while the gate is red. Linked repos carry a local copy of the CLI so the hooks work even with nothing installed globally. Harness hooks are ergonomics; the git hook and the gate are the backstops.

Tier binding (.bench/lines.env)abstract model tiers, bound per repo
The problem

Model names churn constantly. Rules written against concrete model ids rot in months, and a harness that silently substitutes "the closest available model" defeats the declared budget without anyone noticing.

How it works

The workflow speaks only in abstract tiers: cheap, mid, and top. You, the reviewer, bind each tier to a concrete model id in .bench/lines.env and the project profile. The agent resolves tiers through that binding, a hook rejects delegations that step outside it, and if a bound model is reported unavailable the agent re-checks the binding with you instead of letting the harness pick a stand-in.

Two-file context (BENCH.md + BENCH-reference.md)always-loaded rules, on-demand lookup
The problem

Everything an agent must know competes for the same scarce context window. Load it all every session and you pay for file maps and adapter contracts on every message; load too little and cold sessions miss the rules that matter.

How it works

The operating guide (.bench/BENCH.md) is always loaded and carries only what steers generation: roles, the four invariants, the workflow, the communication rules, and the CLI inventory a cold session needs. Everything that's lookup rather than steering (the file map, the skills index, hook layering, the shift adapter contract) lives in .bench/BENCH-reference.md, referenced by path and read only when needed. It costs no tokens until opened.

5
Process

The workflow: five phases, one bug path

Commands are the phases of building a feature, in order. Each one hands off to the next with an explicit recommendation, so you always know where the work stands and what comes next. The numbering below is the real sequence, but the process is right-sized, not ritual: a few-line change may take a lighter path, with your explicit OK before any canonical step is skipped.

1
/bench-shape-ideaturn a loose idea into a sequenced decision map
The problem

Building on top of unresolved decisions produces confident code that answers the wrong question. Big ideas hide questions whose answers change what gets built, and an agent asked to "just build it" will guess at all of them.

How it works

Used only when an idea needs more than one session of decisions. It produces (or resumes) a compact decision map in decisions/<topic>.md: the open questions as tickets, sequenced so answering one unlocks the next, with resolved answers written into the file. The agent works the frontier one question at a time until nothing unresolved still blocks a spec. Shaping runs on the top-tier model, because eliminating uncertainty is exactly what the smartest model is for; once the map is clear, the handoff is a fresh mid-tier session to write the spec.

2
/bench-write-speclock stories, seams, and the definition of done before the loop runs
The problem

An agent iterating without a fixed target drifts: the build's scope quietly grows or shrinks mid-loop, and the tests written at the end conveniently fit whatever got built rather than what was asked.

How it works

Before any substantial build, this phase turns the conversation and decision map into specs/<feature>.md: user stories, implementation decisions, pre-agreed test seams, an acceptance coverage map, and the gate expectations that define done. It synthesizes what's already been discussed rather than re-interviewing you. A spec is one of the most token-heavy artifacts the agent produces, so it runs on the mid tier, on a fresh session that reads the finished decision map instead of inheriting the shaping conversation. The spec stops for your sign-off, then the build runs on yet another fresh session. The target is locked before the loop starts, so the loop can't renegotiate it.

3
/bench-implement-specdo the work at the agreed seams
The problem

Unstructured implementation is where budgets blow up and scope wanders: the agent picks its own boundaries, invents new abstractions, and touches more of the codebase than the change needs.

How it works

Starting from the approved spec, the agent declares its line (tier, effort, iteration cap), then builds in vertical slices at the seams the spec agreed, writing tests first where the spec marked seams for TDD. The acceptance coverage map keeps the target fixed; the phase ends on a green gate. A build that stalls exits early with an honest report instead of grinding past its cap.

4
/bench-review-implementationthe check the gate can't run
The problem

A green gate proves the tests pass; it can't see that the diff violates the repo's conventions, quietly diverges from what the spec asked, or leaves a class of breaking inputs that no test exercises.

How it works

A semantic review of the branch diff on three separate axes: Standards (does it follow this repo's documented conventions), Spec (does it match what was approved), and Coverage (what breaking inputs does nothing exercise). Every finding must meet a citation standard: it points at evidence, not vibes. The review is advisory. It produces findings and persists them for a fix pass, but it never overrides the gate's authority on done-ness.

5
/bench-final-checkrun the oracle, commit on green
The problem

"It's done" is the cheapest sentence an agent can produce. Work that ends on a claim rather than a verdict leaves you to discover the red gate yourself.

How it works

The phase runs the external gate and reports the result plainly, including a red one with the failing output. On green, it lands the work with a path-scoped bench commit, which gates and commits the named files atomically; when the commit finishes a spec, the spec's status flips to implemented in the same commit. Model judgment is never a substitute for the gate here. That is the whole point of the phase.

✕

branch: when the work is a fix, not a build

/bench-debugthe bug path: repro first, fix second
The problem

Pointed at a bug, an agent's instinct is to hypothesize a cause and patch it, and a plausible-sounding fix for the wrong cause passes review, ships, and leaves the bug alive.

How it works

The bug path replaces the feature path the moment something is broken, throwing, failing, or slow. Step one is a tight, red-capable reproduction loop: a command that demonstrably fails because of this bug. That loop, not the agent's theory, is the oracle for the diagnosis and the fix. The fix is right when the repro turns green and stays green as a regression check. The phase also reports any architecture finding that would have prevented the bug.

⟳

outside the sequence: set up once, maintain on cadence

/bench-setup-repoconfigure a repo for Bench, once
The problem

The kit can't guess the parts that are specific to your repo: what the real gate should run, where the seams are, which models the tiers bind to. Defaults here would be silently wrong.

How it works

A one-time interview after linking a repo. It checks the wiring, then fills in what can't be hardcoded: the actual gate script, the project profile (seams, tier bindings, design sources), and optionally a CONTEXT.md seeding the project's mental model and vocabulary. It ends by confirming the gate runs green on the untouched repo.

/bench-what-nextreconcile the roadmap and drain the capture in one reviewed diff
The problem

Parked ideas and process learnings accumulate faster than anyone triages them, and a roadmap nobody reconciles against reality decays into fiction, listing work that already shipped and missing work that emerged.

How it works

The single exit for everything captured along the way. One run reconciles ROADMAP.md against the actual tree, drains parked ideas from IDEAS.md and open entries from the learnings journal into it, refreshes the recommended sequence, and hands you the whole pass as one batch diff to approve. Nothing graduates from "parked" to "planned" without your eyes on it, and it costs you exactly one review.

/bench-assessre-baseline the platform with a fresh ranked backlog
The problem

Day-to-day phases see one diff at a time. Nothing in that loop ever steps back to ask what the whole codebase needs, so structural debt accumulates invisibly between features.

How it works

A periodic pass, run on your cadence, never autonomously. It first verifies the previous assessment's backlog actually landed, then fans out read-only sweeps across the codebase area by area, synthesizes the findings under adversarial re-verification, and replaces ASSESSMENT.md with a dated, ranked, effort-sized backlog. It surfaces; it never merges.

/bench-update-kitsync the kit against upstream, adoption by proposal
The problem

The kit improves upstream, but blindly merging upstream changes into the tool that governs your agents would let the rules rewrite themselves without review, which is the one thing this whole system exists to prevent.

How it works

It diffs the current upstream sources against what Bench already incorporates, tags each candidate change, and runs it through the synthesis discipline (respect closed decisions, assess by the gap it fills, pass the quality loops) before proposing adoption. Accepted changes are recorded in a provenance table and changelog. It proposes; it never auto-merges.

When to start a new session, and on which model

Each phase boundary is also a session boundary, and that's deliberate. A phase leaves behind an artifact written for a reader with no memory (a decision map, a spec, a reviewed branch), so the next phase starts fresh and reads the artifact instead of dragging along a long conversation. The handoff out of shaping is the one to internalize: shaping runs on the smartest model available, because its whole job is to eliminate uncertainty, and by the time it finishes, the session is carrying a large and expensive context. Writing the spec then starts clean on a mid-tier session. This matters because specs and code are the two most token-intensive things an agent produces; neither belongs on the top model by default. The spec is written on the mid tier from the finished decision map, and the build is orchestrated on the mid tier with cheap-tier work at known seams, escalating a stage only where a seam is genuinely uncertain.

Right-sizing

The pipeline is proportional. A genuinely small change can propose a lighter path, but skipping canonical steps is your call, requested before the skip rather than after. A fix for concrete review findings may go straight to fix-and-gate. And when you give a standing rule for changes of a given size, the agent follows it and stops asking.

6
Guidance

The craft skills

Skills are the disciplines the agent loads when a task matches: how to write a spec, where a test belongs, when to delegate. They steer generation rather than enforce it. Think of them as the studio's craft manuals, one per recurring judgment call. Grouped here by the moment they fire.

Deciding & specifying
craft-grillsurface a decision one question at a time
The problem

Asked to clarify requirements, an agent dumps five questions at once. You answer two, the rest get guessed, and the guesses surface as defects weeks later.

How it works

Disciplined elicitation: one sharp question at a time, each leading with the agent's recommended answer and a one-clause why, continuing until nothing unresolved remains. Used inside decision-mapping, before fuzzy specs, or whenever you say "grill me".

craft-specwhat makes a spec's coverage real
The problem

A spec whose acceptance criteria can't actually fail is decoration: the build "passes" it no matter what gets built, and edge cases nobody inventoried become production surprises.

How it works

The authoring discipline behind every spec. Each acceptance-coverage row names a real red signal, meaning a check that demonstrably fails when the story isn't met. Alongside that come a canonical inventory of edge classes to walk, and sizing rules for stories and scope cuts so "out of scope" is a genuine decision, not a dodge.

craft-seamswhere interfaces and tests belong
The problem

Tests placed at the wrong boundary calcify the implementation instead of the behavior, so every refactor breaks them. And every unnecessary abstraction an agent invents is one more surface future sessions must understand.

How it works

Shared vocabulary and principles for placing test seams and designing deep modules: which boundary a test should observe, when an abstraction earns its existence, and why composing an existing seam beats inventing a new one. This is the skill the spec phase leans on when it pre-agrees seams.

craft-adrdecision records that survive amnesia
The problem

Decision records written as narratives of change assume a reader who remembers the before-state. Agent sessions never do, so those records read as noise, and the decision gets relitigated.

How it works

Write the resulting state, not the change: what is decided, why, addressed to a teammate with no memory of the project's history. No file paths or code snippets, because they rot. This is the third invariant turned into a writing method.

Building
craft-tddtest-first without the cost blowup
The problem

Naive TDD with an agent fails two ways: applied everywhere, it multiplies cost on code that never needed it; applied carelessly, the agent writes an implementation that over-fits the test and stops, green but wrong.

How it works

Bounds where and how test-first applies: at the seams the spec marked for it, with red observed before green, and with guards against declaring victory on an over-fit implementation. Read before any TDD pass starts, not during.

craft-clidesign standards for agent-facing CLIs
The problem

Tools built for humans waste an agent's context on prose and ASCII art, and fail in ways an agent can't parse, so the agent burns tokens re-asking and guessing.

How it works

Standards for CLIs whose primary user is an agent: compact structured output, minimal schemas, structured errors that say what to do next, and ambient context surfaced without being asked. Applies when building or reviewing any conforming agent-facing CLI.

craft-design-systemconsume the design system; never regenerate it
The problem

Asked for UI, an agent invents plausible colors, spacing, and components from scratch each time, producing screens that drift from the product's actual design system one hardcoded value at a time.

How it works

On any UI work: pull values from the project's tokens, compose its canonical components, and never hardcode or regenerate what the design source already defines. The skill pairs with whatever design source the project profile names.

Governing the run
craft-linewhich model tier and effort a task deserves
The problem

Model choice is a budget decision, but it's made dozens of times a day in the middle of other work, so it defaults to "the biggest model, just in case", and the spend is invisible until it isn't.

How it works

The judgment half of the second invariant: how to pick the tier and effort for a build, shift, TDD pass, or delegated task, when a tier moves up or down, and how the abstract tiers resolve through the repo's binding. Cheap for plumbing at a known seam, top only where the answer is genuinely uncertain.

craft-delegatewhen to spawn a subagent, and how to trust its answer
The problem

Delegation multiplies throughput and risk together: a vaguely-charged subagent wanders, a shared checkout lets its stray edits land in your files, and its cheerful "done" may describe work that doesn't exist.

How it works

The delegation discipline: when a task is worth spawning for, how to charge and scope the delegate, and when it needs an isolated worktree (any write-delegation does). It also carries the rule that a done-claim is only a claim, verified against the gate and git status before acceptance and never taken on trust.

craft-gatehow to edit the oracle itself
The problem

The gate defines "done", which makes it the most dangerous file in the repo to edit: a well-meaning tweak that can never fail is indistinguishable from safety, and a weakened check fails silently forever.

How it works

The authoring discipline for gate checks: how to add or change one, how to choose its fail posture, and the requirement to prove the check bites by demonstrating the red it's supposed to produce before trusting its green. Reached for before touching the gate script, any enforcement hook, or a gate scaffold.

craft-reviewthe three-axis review and its citation standard
The problem

Agent code review degrades into two failure modes: vague vibes ("consider improving error handling") that no one can act on, or invented problems cited against code that doesn't say what the reviewer claims.

How it works

The judgment behind every review: three separate axes (Standards, Spec, and Coverage) and a citation standard every finding must meet before it's reported. The review phase, a delegate's returned work, a PR, and a self-review before commit all charge from this one discipline. Advisory always; the gate stays the oracle.

Maintaining the kit itself
craft-skillswriting skills that fire reliably and stay lean
The problem

A skill that doesn't trigger when it should is dead weight; one that's bloated taxes every session that loads it. Skills accrete both failure modes unless someone curates them.

How it works

Principles for creating, editing, and pruning skills, covering the kit's own and your project's: how to write triggers that actually fire, how to keep the body lean, and when a skill should be deleted rather than grown.

craft-synthesisfolding changes into the kit without letting rules rewrite themselves
The problem

The kit governs the agents, so a change to the kit is a change to the governor, and an unreviewed one reopens decisions that were deliberately closed or quietly weakens the discipline it came from.

How it works

Every candidate kit change, whether from upstream sync or a learnings-sourced roadmap item, passes the same discipline: respect closed decisions, assess the change by the gap it fills, run three quality loops (legibility, consistency, dogfood), and propose the result for your sign-off rather than merging it.

Memory

Capture: how nothing gets lost between sessions

Sessions end; files persist. Bench routes every kind of in-flight thought to a named file with a defined exit, so a good idea mentioned in passing survives the session that heard it, and nothing graduates into planned work without your review. Capture is conversational: when you want an idea set aside, the agent runs bench idea for you; you never type the chore yourself.

FileWhat lives thereHow it drains
IDEAS.md Parked ideas: tangents worth keeping, captured in one dated line. Graduates into the roadmap only through a reviewed /bench-what-next pass.
ROADMAP.md Planned work with a recommended sequence. Reconciled against the tree each /bench-what-next; items leave when they ship.
.bench/learnings.md The agent's process journal: deviations, uncertain judgment calls, should-have-askeds. The agent captures; it never rewrites its own rules. Each entry gets a verdict in the next /bench-what-next; generalizable ones become reviewed kit improvements.
decisions/ Decision maps from /bench-shape-idea: open tickets and resolved answers. Feeds /bench-write-spec once no open ticket blocks the build.
specs/ Build specs with a status lifecycle: staged, then implemented at the green gate, then promoted and deleted on merge. Status flips ride the green commit; retired specs keep their history via bench spec history.
reviews/ Persisted findings from semantic review that await a fix pass. Cleared by the fix pass, or deleted deliberately when you accept the residual risk, named in the final check.
CONTEXT.md The project's current mental model and shared vocabulary, the first thing a cold session reads. Maintained as the model evolves; always present-tense (invariant three).
projects/<name>.md The project profile: the gate's shape, the seams, the tier bindings. Owned by the reviewer; edited through setup and deliberate decisions.
ASSESSMENT.md The latest dated platform assessment with its ranked backlog. Wholly replaced by the next /bench-assess, which first verifies the old backlog landed.
The loop closes

Notice the shape: ideas and learnings flow in from conversation, drain through one reviewed batch into the roadmap, and become decisions, then specs, then gated commits. What the process learns about itself follows the same path back into the kit. Every arrow in that loop passes through your review exactly once, which is how the system improves from real use without ever changing its own rules behind your back.

The Bench Field Guide is an orientation to the Bench agent-development kit. Start with the two roles, trust the gate over any claim, and let the workflow phases carry the rest. The canonical rules live in .bench/BENCH.md in your repo; this page is the guided tour, not the source of truth.
